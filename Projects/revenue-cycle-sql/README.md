# Revenue Cycle Claims Analysis (SQL + Excel)

A repeatable, reusable revenue cycle analytics workflow built the way a **centralized
healthcare analytics team** works: clean the data once, define each metric once, parameterize
by the axes every hospital shares (payer, service line), so the same logic reruns across client
engagements. Scope is **mid revenue cycle** — charge capture, coding, denials, managed care.

> **Headline finding:** clean (first-pass) claims are denied **3.9%** of the time; claims that
> needed rework are denied **55.7%** of the time — roughly **14× higher**. Front-end claim
> quality is the single upstream lever that drives denials, AR aging, and ultimately collected
> cash. This project quantifies that chain end to end.

---

## The story these five metrics tell (one causal chain, not a dashboard)

1. **Clean claim rate 83.8%** → the 16% of claims that get reworked are denied at **55.7%**
   (vs 3.9% for clean claims).
2. → that feeds a **denial rate of 12.2%**, of which **~60% is preventable front-end error**
   (authorization, eligibility, coding).
3. → denied and reworked claims sit unpaid: **78.5% of open AR dollars are 90+ days** aged.
4. → leaving **net collection at 91%** of contractually owed dollars — healthy, but the leakage
   traces straight back to step 1.

**The lever:** fixing front-end cleanliness attacks the 55.7%-denying rework population, the
60%-preventable denials, and the aged AR at once. That's a recommendation, not a chart.

---

## About the data (read this first)

The dataset is **synthetic** — 5,000 claims generated by [`scripts/generate_data.py`](scripts/generate_data.py)
with a fixed random seed. Real claims data is PHI and cannot be shared in a public portfolio, so
the data is **modeled on real revenue cycle structure**: payer-specific contract rates, denial
behavior that varies by payer, charges inflated above allowed amounts, and realistic data-quality
defects (inconsistent payer spellings, missing pay dates, duplicate claims, impossible dates).
Because the generating process is known, every computed metric is **validated by reconciling it
back to the parameters it was built from** — e.g. the by-payer denial rates recover the encoded
Medicaid-high / Medicare-low ordering exactly.

Everything regenerates from the seeded script, so the repo ships **no data files** (see
`.gitignore`); run the script to reproduce the database bit-for-bit.

## The analytical workflow

A real engagement workflow, in order — each stage mirrors what a consultant's analyst does on a
client extract:

| Stage | File | What it does |
|---|---|---|
| **A. Exploration & profiling** | [`sql/02_profile.sql`](sql/02_profile.sql) | Row/distinct counts, category distributions, numeric ranges, date spans. Get to know the file. |
| **B. Missingness & data quality** | [`sql/03_quality_checks.sql`](sql/03_quality_checks.sql) | Null rates + logical-consistency checks, each reconciled to a known ground-truth count. |
| **C. Cleaning & standardization** | [`sql/04_clean_views.sql`](sql/04_clean_views.sql) | The trusted layer: 28 payer spellings → 7 canonical payers, dedup, quarantine corrupt rows, derive helper columns. |
| **D/E. Grain & metric selection** | [`METRIC_DEFINITIONS.md`](METRIC_DEFINITIONS.md) | Lock the grain and every metric's exact numerator/denominator before computing. |
| **F. The five metrics** | [`sql/metrics/`](sql/metrics/) | Denial rate, reason mix, days in AR, net collection, clean claim rate. |
| **Segmentation** | [`sql/99_segmentation.sql`](sql/99_segmentation.sql) | All five metrics at payer × service-line grain in one reusable, rollup-correct view. |

**Key design principle — clean once, reuse everywhere.** Metrics never touch raw tables; they
read a single trusted view (`v_claims_analytic`). The segmentation layer stores *additive
components* (counts, dollar sums) so any rollup is correct at every grain — and its rollups
reconcile to the standalone metric files to the decimal, proving the consolidation is right.

## Metric definitions

Full numerator/denominator/inclusion rules and the interviewer probe for each metric are in
**[METRIC_DEFINITIONS.md](METRIC_DEFINITIONS.md)**. The headline definitions:

- **Denial rate** — denied claims / all claims (and dollar-weighted on charges). Initial denial.
- **Denial reason mix** — distribution of denied claims by CARC category, with a preventable
  (auth + eligibility + coding) rollup.
- **Days in AR** — paid-claim throughput (median + mean days to pay) **and** open-AR aging
  buckets (0–30 / 31–60 / 61–90 / 90+), clock from date of service.
- **Net collection rate** — paid / **allowed** (not charge). The net-vs-gross distinction is the
  managed-care literacy test: gross looks like 45% only because charges are inflated list prices;
  net is 91%, and the gap is the contractual adjustment.
- **Clean claim rate** — first-pass-clean / submitted. "Clean" = no rework, stricter than
  not-denied; the upstream leading indicator.

## Headline numbers

| Metric | Value |
|---|---|
| Denial rate (count / dollar) | 12.2% / 12.3% |
| Preventable share of denials | ~60% |
| Days to pay (mean / median) | 39 / 35 |
| Open AR in 90+ bucket | 78.5% of open dollars |
| Net collection rate | 91.0% (gross 45.1%) |
| Clean claim rate | 83.8% |
| **Denial rate: clean vs reworked** | **3.9% vs 55.7% (~14×)** |

By payer, the segmentation recovers the real pattern: Medicaid highest denial (18.6%) and
slowest pay (52 days); Medicare lowest denial (7.5%) and fastest pay (31 days); net collection
flat ~91% across payers (collection performance), while gross swings 25–82% (contract rates).

## Reproduce

```bash
cd Projects/revenue-cycle-sql
python3 -m venv .venv && ./.venv/bin/pip install -r requirements.txt
./.venv/bin/python scripts/generate_data.py          # -> data/raw/*.csv

sqlite3 revenue_cycle.db < sql/00_schema.sql          # DDL

sqlite3 revenue_cycle.db < sql/04_clean_views.sql     # Stage C (trusted layer)
sqlite3 revenue_cycle.db < sql/metrics/denial_rate.sql
sqlite3 revenue_cycle.db < sql/metrics/denial_reason_mix.sql
sqlite3 revenue_cycle.db < sql/metrics/days_in_ar.sql

sqlite3 revenue_cycle.db < sql/metrics/clean_claim_rate.sql
sqlite3 revenue_cycle.db < sql/99_segmentation.sql    # reusable scorecard
```

## SQL techniques used

Star-schema DDL · views as a trusted staging layer · CTEs · conditional aggregation
(`SUM(CASE WHEN …)`) · window functions (`ROW_NUMBER` for dedup, `SUM() OVER ()` for
share-of-total, hand-built median) · null-guard parameterization
(`:param IS NULL OR col = :param`) · conditional-aggregation pivots · additive-component
rollups that stay correct at every grain.
